# Macro Crash Check — Project Instructions

_Served to Claude Desktop by the crash-check MCP server's `get_instructions` tool, read fresh from the local working tree (not attached as project knowledge, since 2026-11-15)._

This project runs recurring "macro crash check" analyses using a live automated pipeline instead of a static pasted prompt. When the user says "run crash check" or "run check":

**Anti-anchoring order matters here — follow the numbered sequence exactly, do not reorder or peek ahead.** Steps 1-6 deliberately avoid any tool that exposes a prior crash-probability value or prior narrative text, so the scenario tilt chosen in step 7 (the split and crash_probability_pct are derived from it — see step 7) is formed independently. Step 8 is the *only* point where the prior numbers are retrieved, specifically to build a delta-log — never to revise the judgment already committed to in step 7.

**This workflow always ends in `write_snapshot` + `write_full_report` (steps 11-12) — every single time it completes, regardless of whether anything changed since the last run, regardless of whether it was a calm/quiet day, and regardless of whether it "feels like" a routine refresh rather than a full report.** There is no "skip persistence because nothing changed" condition anywhere in this process — do not infer one. `crash-check-rules.md`'s "automated indicator refresh vs. full chat-triggered report" distinction is about display formatting for a different (multiple-checks-per-day) cadence; it does not apply here and is not a reason to skip steps 7-12. A quiet day is still a real daily data point and must be recorded — silently skipping it creates gaps in the history that the confirmation-window and delta-log mechanisms depend on. The *only* valid reason to stop early and not persist is the freshness check in step 1.

1. Call `get_indicator_panel` for the current 6-indicator RED/AMBER/GREEN panel, RED count, and wave status. This tool returns mechanical data only — no prior run's crash probability or narrative (its `scenario_prior` is fixed history, the same every day in the same band) — by design, so this step can't anchor you. Its `distance_to_red` shows how close each indicator is to its RED line; quote it, don't recompute it. Its `scenario_prior` is the historical starting point for step 7. **Check `data_freshness.is_fresh` first, before anything else.** If it's `false`, the daily GitHub Action ingestion hasn't run yet today (or failed) — the panel is a stale prior-day snapshot. Stop here, tell the user the data isn't current yet (include `data_freshness.note`), and do not proceed with the rest of this workflow on stale data. (Scheduled unattended runs — the weekday 6:30pm ET task, which reads the 6pm post-close ingest — should treat this the same way: skip persisting anything this run rather than writing a stale-data analysis.)
2. Call `get_trigger_status` for the personal decision triggers and Warsh Fed classification status. **Use `fed_event_trigger`/`inflation_print_trigger`'s `current_target_date`/`current_target_label` as this run's anchor for the Fed-event and inflation-print triggers** — do not independently recall or guess which FOMC meeting or CPI release is "the current one" from a prior session or the old master-prompt doc; that's exactly the staleness bug this replaced (a real report kept showing "July FOMC" long after it should have rolled to September). If `calendar_needs_update` is true for either, tell the user the local calendar file needs new dates added rather than reporting a guessed or stale date. `fiscal_event_trigger` (Treasury quarterly refunding) works the same way; its `note` criteria are in `get_rules` "Fiscal-event trigger".
3. Call `get_context_indicators` for supplementary macro context (financial stress/conditions indices, 2s10s yield curve spread, breakeven inflation, bank lending standards, reverse repo, the SOFR−IORB repo-stress spread, MOVE bond volatility, jobless claims, credit card delinquencies). These are informational only — never treat them as part of the RED count or wave-authorization decision, which comes exclusively from step 1's 6-indicator panel.
4. Call `get_portfolio_snapshot` for personal account balances/allocations — this data is local-only, never repeat exact dollar figures back in a way that would get persisted to `write_snapshot`'s `notes` field. **Don't put the rate-reset trigger in `write_snapshot`'s `trigger_status`:** it describes a personal account, so `write_snapshot` keeps only the four market-event triggers on the public row and `write_full_report` records `rate_reset_trigger` privately on its own. Report `rate_reset_trigger.status` and `.note` in the chat summary verbatim, character-for-character — don't choose your own status (a recurring event can still be "fired"; the tool has already accounted for that). Trigger re-checking is still an active step every run for the market-event triggers, which do need judgment (was the event's outcome hawkish/dovish, etc.) — not something to do only if it happens to come up. **Also fetch `get_rules` "Personal workflow notes" once this run, if it exists** (local, account-specific steps for steps 9 and 12; it holds no prior probability or narrative). **Also read `deployment_readiness`** (deployment-instrument readiness, see `crash-check-rules.md` "Deployment Instrument Selection" via `get_rules`): in step 9's crash readiness summary, report the GREEN/AMBER/RED slot counts and any `red_slots` as-is, and if `review_status` is `DUE_SOON` or `OVERDUE`, say the quarterly instrument review is due (with `next_review_due`) and that it runs as part of "run portfolio review". If `registry_valid` is false, report the errors.
5. **If a wave is active (`wave_active` is not `NONE`) or a crash type has been diagnosed, call `get_deployment_plan`** for the exact dollar breakdown per fund. Never compute wave/crash-type dollar amounts yourself from percentages in the rules doc — this tool does that arithmetic deterministically; just report its output (cross-referenced against `get_portfolio_snapshot` for actual fund names, since this tool's fund labels are generic).
6. Do qualitative synthesis via web search: geopolitical developments, Fed rhetoric, earnings commentary, crash-type diagnosis. Also report NVDA/ORCL/CRWV CDS against the baselines in `get_rules` "AI single-name credit stress", giving each new quote's tenor and source: a supporting signal only, never a Type D criterion. The mechanical indicator bands, RED count, and wave authorization always come from the tool output — never re-derive or override that classification yourself.
7. **Commit to this run's scenario tilt now**, using only steps 1-6's data (changed 2026-11-17; rules in `get_rules` "Crash-Probability Scoring Methodology"). You no longer write a bull/base/bear/crash split. Step 1's `scenario_prior` gives the historical split for days in today's drawdown risk band over the next 63 trading days (about 3 months). Pick **one** tilt against that history:
   - `in_line`, the default, when nothing clearly differs from what drawdown + VIX already capture;
   - `higher` or `lower` only for something those two can't see (credit, fiscal, an upcoming event, a divergence). Each moves a fixed 5 points between bull/base and bear/crash.

   Write 1-3 `tilt_reasons` for `higher`/`lower` (up to 3 for `in_line`), each quoting a number from steps 1-6, e.g. "HY spread +45bp in 20 days while VIX is flat". Read the resulting split from `scenario_prior.split_by_tilt` (don't compute or invent your own numbers). `crash_probability_pct` is bear + crash: the chance of a 10%+ S&P fall within 63 trading days. Write the tilt, its reasons and the split down (in your working reasoning) before proceeding. Do not call `get_latest_snapshot` or look at any prior probability/notes before this step is done. Once step 8 shows you the prior values, you are not allowed to revise what you just committed to, only to explain the difference. For up to 3 upcoming events (e.g. the next FOMC), also form event-conditional branches now (outcome, probability, split each, same buckets and horizon; their probability-weighted splits must be within 5 points of this run's split; rules in `get_rules` "Event-conditional scenarios"); they are written only in step 11.
8. **Now call `get_latest_snapshot`** to get the last full report's stored tilt, split and narrative (the tool specifically finds the last row that had a probability, not just the chronologically-previous row — most rows are bare automated refreshes with no probability at all), purely to build the delta log (e.g. "tilt in_line -> higher; 10%+ fall 8% -> 13%") and describe what changed. If the delta marks `crash_probability_pct` as "definition changed", the prior report used the old undefined split: say the two aren't comparable instead of reporting a move. This is a framing/reporting step, not a re-estimation step — the tilt was already locked in step 7.
9. **Lead the assessment with a "Current assessment" block** — 3 observations drawn from data already gathered in steps 1-3 (not fresh research), the single strongest counterargument to whatever headline read those 3 observations suggest, and the next concrete thing to watch for. Each of the 3 observations must cite an actual number already in hand this run (e.g. "0 of 6 RED; VIX 17.1; HY spread 271bps" or "only 3 of 11 sectors have positive 30-day NAV returns despite 10 of 11 being positive over 180 days") — this is a structured summary of data you already have, not a new judgment call, and must not become another unanchored discretionary field. Then produce the full assessment: the drawdown risk band first (see below; it is the headline risk reading), then the 3-month LLM view from step 7 (history for the band, your tilt with its reasons, and the resulting chance of a 10%+ fall against the historical figure), delta log (from step 8), ranked triggers, contextual indicators (from step 3), **the drawdown risk band (`drawdown_risk_band` from step 1's `get_indicator_panel` call — report its `band` with its `historical_hit_rate_pct` against `base_rate_pct`, not a re-derived percentage, as its own section, ahead of the LLM view; if `status` is `ALREADY_BREACHED` say the S&P is already past 10% and the band does not apply, and if `UNAVAILABLE` say "unavailable this run," never a reading of zero. It replaced the statistical hazard model on 2026-11-17; do not quote the old model)**, personal portfolio impact (from step 4, chat-only — not persisted), deployment plan (from step 5, if applicable, chat-only — not persisted), trigger status, the account-specific checks in `get_rules` "Personal workflow notes" (if that section exists), crash readiness summary.
10. **End with a plain-text summary in chat — no HTML artifact, no file, and don't search project knowledge for a dashboard template (there isn't one any more; changed 2026-11-13).** Lead with step 9's "Current assessment" block, then follow the scan order in `crash-check-rules.md`'s Formatting Requirements (fetch it with `get_rules` "Formatting Requirements" before writing): RED ALERT (if any), the drawdown risk band, the 3-month LLM view (tilt, reasons, chance of a 10%+ fall vs history) and its change vs the prior full report, the 6-indicator panel with confirmation status, crash-type diagnosis (if any), wave status and the watchlist, then any notable contextual indicators. Then the personal portfolio impact from steps 4–5 (dollar figures are fine here — chat only, never persisted), any action items, and finally two links: the public dashboard (https://marketstress.org/) for the charts and full indicator detail, and the private Full Report page (https://market-sentiment-full-report.pages.dev/) for the watchlist, crash-type diagnosis and portfolio context. Both pages are rebuilt from what steps 11–12 save, so the summary doesn't need to reproduce them.
11. Call `write_snapshot` with the qualitative synthesis: `prior_state` (step 1's `scenario_prior.state`), `scenario_tilt` and `tilt_reasons` from step 7, notes, delta log. There are no split or probability fields: the tool derives and stores the split and `crash_probability_pct` from the frozen prior and your tilt. If it rejects the call because the band changed since step 1 (a newer rule-engine run), re-run step 1 and redo step 7. Keep `notes` and `tilt_reasons` to macro/market narrative only — no personal dollar amounts, no account-specific deployment instructions. **Pass `delta_log` as the same structured list you're already building for the HTML artifact's colored delta log** (each `{sign: "pos"|"neg", text}`) — this was previously only ever rendered live and never persisted, which is why the public dashboard couldn't show it. Omit it entirely on a run with no prior full report to diff against (step 8). **Re-check every trigger from step 2 against this run's data (step 4's portfolio snapshot, step 6's research) before writing — the default is to actively verify each one, not to silently carry forward whatever status/note was already stored.** For the fed-event, inflation-print and fiscal-event entries specifically, take `date`/`name` directly from step 2's `fed_event_trigger`/`inflation_print_trigger`/`fiscal_event_trigger` `current_target_date`/`current_target_label` — do not recall or reconstruct these yourself; only `status` (fired/approaching/pending) and `note` require your own judgment on that meeting's/release's actual outcome. For earnings-guidance, explicitly roll the target forward to next quarter's earnings once the current quarter's has been assessed — no deterministic calendar backs this one (company earnings dates aren't published far enough in advance to hardcode), so this stays a judgment call, the same treatment you're already applying well to ad-hoc catalysts like a Fed Chair's first Jackson Hole keynote. Include any updates (Warsh classification, Fed pivot signal, trigger statuses) in this same call. Pass step 7's branches as `conditional_scenarios`, and a `conditional_outcomes` entry for every event step 8 listed as due (a branch name, "other", or "unresolved" with a reason); never write your own branch probabilities into trigger notes (market-implied odds with a named source, e.g. CME FedWatch, are fine). **Macro & Fiscal narrative (`macro_narrative`, added 2026-11-18):** compare step 3's `fiscal_dominance_checklist`, yield-curve and context readings with step 8's `last_macro_narrative` (its text and `run_at`). Pass a new one if `last_macro_narrative` is null, or if a Macro-tab reading changed since then: a checklist item flipped, a stage count moved, a monthly or quarterly release landed, or the curve classification changed. Otherwise omit the field and the public page keeps the last one. When you write it: 3-5 sentences, under 900 characters, plain English for a first-time reader, saying what the readings add up to (where the strain is, whether markets are pricing it, what the curve says). Quote the numbers. If you call a check close to stress, state that check's own rule and which part is or isn't met. No forecasts, no buy/sell calls, no personal or account details. It is public and is shown with an AI mark.
12. Call `write_full_report` with the crash-type diagnosis (structured: `type` + a `criteria` list of `{name, status, detail}`, if one was reached in step 6 — **omit this field entirely if not, do not pass `null`**, the tool rejects that) and `portfolio_context` — the qualitative-only parts of the personal portfolio impact from step 9 (dry-powder status, the account-specific checks from "Personal workflow notes", crash readiness narrative), framed relatively ("the opportunity-cost gap is significant and unchanged") rather than restating any dollar figure. Never include any account's actual dollar amount here — those lines stay chat-only, always. The watchlist portion of this table is recomputed by the tool itself from live prices; you don't supply it.

The Risk Radar (six 0-100 discretionary scores) was retired 2026-11-13: don't produce one in either workflow, and ignore `risk_radar` fields on old rows.

Formatting and threshold rules (indicator bands, wave triggers, crash-type criteria, KPI display format) are in `crash-check-rules.md`, which is **not attached as project knowledge** (changed 2026-11-13: attached, it came back as search fragments once project knowledge outgrew what Claude Desktop loads in full). Read it with the `get_rules` tool, one section at a time: `get_rules` with no section lists them all, and `get_rules` with a section name (e.g. "Formatting Requirements", "Stage 1", "Deployment Instrument Selection") returns that section in full. Whenever a step or a tool description cites a section of the rules doc by name, fetch it this way. Treat what it returns as the source of truth; never reconstruct a rule from memory or from a project-knowledge search result. In the chat summary, state each status in words (GREEN / AMBER / RED, confirmed or pending); the two web pages own the visual design.

If the S&P has fallen ≥10% from its ATH since the last check, lead with a RED ALERT banner (drawdown %, wave triggered, RED count, one-sentence action) before anything else — skip the macro narrative preamble in that case.

Always include the standard disclaimers (informational only, not investment advice, consult a CFP/RIA/cross-border CPA as applicable) at the end.

## Portfolio Opportunity Review (on-demand — separate from "run crash check")

When the user says "run portfolio review" (no fixed schedule — this only runs when explicitly triggered, unlike the recurring crash check):

1. Call `get_portfolio_drift` for the mechanical target-vs-actual % check across all accounts. Report any `DRIFTED` funds and `standing_flags` as-is — these come from the tool, not your own comparison. Note that the tactical account is deliberately excluded from drift classification (its dry powder is wave-gated, not neglected) — its status comes from `get_deployment_plan` instead.
2. Call `get_watchlist_status` for the current watchlist ticker prices vs. Wave 1/2/3 targets and BUY_ZONE/WATCH/WAIT status. Report status as-is — never eyeball or estimate prices yourself.
2b. **Deployment fire drill.** Call `run_deployment_fire_drill` with `through_wave: "WAVE_3"` (once without a crash type, and once with the crash type most consistent with the current regime). Report `summary.pct_blocked`, the RED/AMBER lines and their `reasons`, and which instrument each line would actually buy — as-is, chat-only. If `instrument_registry.review.status` is `DUE_SOON` or `OVERDUE`, also run the quarterly instrument review from `crash-check-rules.md` "Deployment Instrument Selection" (via `get_rules`): for each slot, re-check primary and backup against the selection criteria (role fit, cost, fund risks such as closure/merger/manager change/outflows, route), and propose registry edits with a one-line reason. Never judge an instrument on recent returns, and never apply an edit without the user's approval — the registry (`local_state/deployment_instruments.yaml`) is edited by hand, including bumping `verified_on` and `last_full_review`.
2c. **Fund filings and role fit.** Call `check_fund_filings` and report its `events` as-is (structural ones first), plus the `manual_check` list. Only call `acknowledge_fund_filing` after the user has looked at an event. During the quarterly instrument review, also call `get_role_fit_metrics` and report the readings per slot alongside `proposed_bands_not_adopted`. The bands are not adopted until the 2027-02-02 review, so never present a reading as a pass or fail, never propose a swap from it, and never weigh returns.
2d. **Exchanges.** Whenever the user confirms a plan exchange was submitted, record it: `record_wave_deployment` (with `bought`/`sold` fund names as shown on the plan website) for a wave, `record_exchange` for anything else. The exchange log is what plan trading limits are counted against.
3. Do deep qualitative research: read BlackRock's Geopolitical Risk Dashboard, the current WEF Global Risks Report, and at least one mainstream bank/asset-manager macro outlook (e.g. JPMorgan's Guide to the Markets). Cross-reference these against the current macro regime (`get_latest_snapshot`) and the drift/watchlist results from steps 1-2.
4. For each watchlist ticker, re-underwrite the thesis: is it still the best expression of its theme given current conditions? Should the target price, max position, or the ticker itself change? Propose specific changes with reasoning — do not change anything without the user's explicit approval first. Apply any ticker-specific re-underwrite instructions in `get_rules` "Personal workflow notes" (if that section exists), connecting each named indicator to that ticker's thesis rather than reporting it as generic macro context.
5. If the user approves changes, call `write_watchlist` with the complete updated ticker list (full replacement, not a partial patch) and a `change_summary` — this syncs both the local file and Supabase's ticker list automatically, no manual follow-up needed.
6. **Render the review as an HTML artifact, using the review template as the base** (fetch it with `get_instructions` and `document: "portfolio_review_template"`) — reuse its structure, CSS, and component classes (verdict hero + stats, allocation bars with target-tick markers, standing-flag cards, ticker cards with proximity meters + thesis chips, macro cross-reference cards); replace the example content with this run's live values. Do not just answer in plain chat text.
7. Summarize: what changed since the last review (if any), current portfolio drift status, current watchlist status, and an overall "is my portfolio still positioned right for this macro/geopolitical climate" verdict — this is the verdict headline at the top of the artifact.
8. Call `write_portfolio_review` with the verdict, summary, macro cross-reference synthesis, and per-ticker `thesis_verdict`/`reasoning`/`proposed_change` from step 4 — this merges the review into the Full Report page. Call this every time a review completes, whether or not the user approved any ticker changes (that's the separate `write_watchlist` gate in step 5). Portfolio drift is recomputed by the tool itself from the local file — don't pass it. Pass `decisions`: one entry per proposal that needs the user's approval (watchlist target changes, instrument-registry edits from step 2b, fund filings to acknowledge, rebalances), each with a short `title`, a one- or two-sentence `detail`, its `kind` and the `ticker` if any. Pass `[]` if nothing needs a decision; omit anything the user already approved and you applied this session. No dollar figures. The deployment fire drill doesn't need passing: `write_full_report` stores a dollar-free summary of it every run.

Position-sizing dollar figures (`max_position_usd` and anything from `get_portfolio_snapshot`) are still chat-only, never persisted anywhere — that rule is unchanged. Drift percentages, watchlist status, and the qualitative thesis/verdict/macro-research content now do get persisted (`write_portfolio_review`), which is what makes the Full Report page's Portfolio Opportunity Review section possible — the tool itself rejects the write if a real portfolio dollar figure slips into any text field anyway. The dashboard's visual design in `portfolio-review-template.html` (colors, cards, layout) is fixed — treat its CSS custom properties and status-color semantics as fixed, not something to redesign each run.

## Allocation Analysis (on-demand — separate from both workflows above)

When the user asks for an allocation analysis ("run allocation analysis", or the account-specific phrase named in `get_rules` "Personal workflow notes"), fetch `get_rules` "Allocation Analysis Prompt" and follow it exactly. The prompt is local and private, served by `get_rules`. It's a deeper, occasional review of whether the tactical account's fund mix and dry-powder strategy still fit current conditions (look-through exposure, cost of carry, crash-type exposure, stress test), not a substitute for "run portfolio review". It is chat-only: call no write tools (`write_snapshot`, `write_full_report`, `write_portfolio_review`, `write_watchlist`, `record_wave_deployment`). If `get_rules` has no such section, say so and ask the user to paste the prompt rather than improvising the steps.
